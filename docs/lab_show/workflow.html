04 · Submission workflow

From portal to results.

A submission is a packaged container, not a paper. Sites opt in study-by-study. FLAIR checks the code before any site sees it. Only aggregate JSONs come back.

Technical architecture

What sits at each site, what crosses the wire, what lives in the central FLAIR. The site's data steward is the human who runs the container and ships the anonymized aggregate JSONs back — that role is what makes the federated handshake auditable.

The two-stage visibility is what makes site-PI review tractable. Sites see what they'd be running before they're asked to vouch for it.

What the site sends back

Only the four standardized FLAIR report JSONs, one per task: table1.json, tripod_ai.json, fairness.json, curves.json. Every cell HIPAA-suppressed. Every subgroup with n < 10 dropped. Every output stamped with task_script_sha256 so the aggregator can prove two sites ran byte-identical code.

No raw predictions. No patient identifiers. No model gradients. No logs that could leak counts.

Failure modes the portal catches early

  • Container makes a network call (egress trace flags it).
  • Code imports a banned API (e.g., urllib.request, socket).
  • Model object can't load deterministically twice in a row (hash mismatch).
  • End-to-end run on MIMIC-CLIF doesn't produce valid report JSONs.
  • Output JSONs leak counts below threshold.

All caught at the portal before any consortium site sees the submission.
