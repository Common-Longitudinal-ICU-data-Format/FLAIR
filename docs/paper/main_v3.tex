\begin{abstract}
\noindent\textbf{Background.} AI clinical decision support tools are proliferating faster than the evidence needed to judge whether they work across hospitals. ICU models are often evaluated at one or two sites, or on a small number of public electronic health record datasets, rather than tested broadly across independent hospitals. Public benchmarks are essential for method development, but repeated tuning on the same datasets can produce benchmark saturation and illusory generalizability. Traditional multi-site validation requires bilateral data use agreements and patient-level data transfer, so it often takes years and reaches only a few sites.

\noindent\textbf{Methods.} FLAIR is an open-source federated benchmark and model-to-data protocol for ICU prediction research. It uses the Common Longitudinal ICU Format (CLIF), a critical-care data format with shared table structures and mCIDE categories. Developers build and test code on public MIMIC-CLIF data. After Benchmark Committee review, the same code or container can run locally at participating CLIF sites. Five binary benchmark tasks are included: daily in-hospital mortality, daily long-term acute care hospital discharge, extubation failure within 24 hours, sepsis within 6 hours, and unplanned ICU readmission. Each site returns aggregate report bundles for cohort characteristics, discrimination, calibration, decision curves, lead time, subgroup performance, and audit metadata. Patient-level rows remain at the site.

\noindent\textbf{Results.} In the v2 baseline runs, an XGBoost count-feature model trained on MIMIC-CLIF had internal-test AUROCs of 0.864 for daily mortality, 0.789 for LTACH discharge, 0.696 for extubation failure, 0.693 for sepsis, and 0.641 for ICU readmission. At the first external reporting site, Rush, AUROC was lower for all five tasks: 0.748, 0.658, 0.565, 0.407, and 0.509, respectively. Site-level results for additional institutions remain TODO. \todo{Confirm or regenerate T4 sepsis results against the current CDC Adult Sepsis Event task implementation before submission.}

\noindent\textbf{Conclusions.} FLAIR is intended to make external validation more reproducible and more practical for ICU AI. It provides public development data, inspectable task definitions, committee-reviewed model-to-data execution, and aggregate-only reporting for a growing leaderboard. The current release is a benchmark and protocol resource, not evidence of clinical utility for any specific model.
\end{abstract}

\section{Introduction}

The bottleneck in ICU clinical AI is no longer the supply of models. Predictive algorithms for sepsis, acute kidney injury, extubation readiness, ICU mortality, and hospital operations continue to appear in the literature. The harder problem is evidence: whether a given model behaves acceptably in hospitals that did not build it. That evidence gap is partly an access gap. Representative, multi-institutional ICU data are usually not available to the team that needs to test a model.

External validation of flagship electronic health record-based clinical decision support has remained narrow. The Epic Sepsis Model, used across many United States hospitals, was first independently evaluated at one site, where discrimination fell to an AUC of 0.63 against vendor-claimed ranges of 0.76 to 0.83 \citep{wong2021external,habib2021jamaeditorial}. Duke's Sepsis Watch required years before external assessment at another site \citep{sendak2025sepsiswatchportability}. The Targeted Real-time Early Warning System reached five sites within one health system \citep{adams2022trews}. Mayo Clinic's electrocardiogram-based low-ejection-fraction screen, developed through a regulatory pathway, required multi-year coordination to cover several external sites \citep{carter2025mayoecgai}. These examples show that serious validation is possible, but the process does not scale easily to the pace of model development.

Public benchmarks have helped but cannot solve the problem alone. ICU benchmarks built on MIMIC, eICU, HiRID, AUMCdb, and related datasets are essential for reproducible development \citep{vandewater2023yaib,yeche2021hirid}. They also inherit the selection biases of their source data \citep{roosli2022mimicfairness}. Repeated tuning against a fixed public benchmark can make performance appear more transportable than it is \citep{recht2019imagenet,chekroud2024illusory}. Private multi-site validation addresses that weakness, but the usual route - data use agreements followed by transfer of de-identified patient-level data to an analytic center - is slow and narrow.

Several communities have shown pieces of a better approach. OHDSI and LEGEND federate studies across the OMOP common data model \citep{reps2020ohdsistroke}. MedPerf demonstrates portal-orchestrated model-to-data benchmarking for medical imaging \citep{karargyris2023medperf}. The FeTS Challenge used federation for imaging-based training rather than validation \citep{pati2022fets}. OpenSAFELY showed that code can travel to national-scale clinical data without moving patient rows \citep{opensafely2021naturemedicine}. DREAM Challenges introduced model-to-data challenge infrastructure, and the EHR DREAM Challenge showed that this pattern can support EHR-based mortality prediction \citep{guinney2018dream,bergquist2024ehrdream}. What has been missing for ICU EHR-based clinical decision support is the combination of a critical-care data standard, a reusable task catalog, and a standing federated validation protocol.

FLAIR (Federated Learning Assessment for ICU Research) was built to fill that gap. The core idea is simple: the model goes to the data, and aggregate evaluation reports come back. A developer writes code against MIMIC-CLIF, the public CLIF version of MIMIC-IV \citep{johnson2023mimiciv,johnson2016mimiciii}. After review, the same code can run inside each participating institution. The site returns tables and metrics, not patient rows.

This paper describes FLAIR as a dataset, benchmark, and protocol resource. The dataset layer is CLIF, with MIMIC-CLIF as the public development entry point. The benchmark layer is a seed set of five ICU prediction tasks implemented as inspectable Python cohort builders. The protocol layer is a repeatable model-to-data workflow with a Benchmark Committee, a FLAIR Portal, local execution by Site Leads and Data Stewards, and aggregate-only reporting to a leaderboard. FLAIR is not a clinical deployment system and does not certify models for bedside use. Its purpose is narrower: to make multi-site ICU model evaluation reproducible, auditable, and feasible without routine transfer of patient-level data.

\section{Methods}
\label{sec:methods}

FLAIR is implemented as the \texttt{flair-benchmark} Python package and command-line interface. The package builds task cohorts from CLIF tables, provides optional point-in-time feature extraction, and creates aggregate report bundles from prediction files. Each cohort row has a \texttt{prediction\_dttm}, which is the no-future-data boundary. Models may use data at or before that timestamp and no data after it.

We describe FLAIR as three coupled artifacts: a data layer, a task layer, and a protocol layer. The data layer is CLIF, with MIMIC-CLIF as the public development entry point. The task layer is a set of benchmark definitions implemented as single-file Python modules. The protocol layer is a model-to-data execution process in which reviewed code or containers run locally at each site and return aggregate JSON reports.

The public workflow has five steps: configure a CLIF site, build a task cohort with \texttt{flair load-task}, optionally extract features with \texttt{flair fe-wide} or \texttt{flair fe-meds}, train or apply a model, and create aggregate reports with \texttt{flair build-report}. Binary prediction files carry \texttt{prediction\_id}, the task label, split, and \texttt{y\_prob}. The report builder scores the held-out test split and writes JSON files that can be pooled centrally.

Reporting follows the general structure expected for clinical prediction models, including discrimination, calibration, threshold behavior, and subgroup analysis \citep{collins2024tripodai}. The FLAIR report bundle populates many of the elements expected by TRIPOD+AI. A Datasheet for Datasets framework \citep{gebru2021datasheets} informs the public MIMIC-CLIF cohort documentation, and a Model Card framework \citep{mitchell2019modelcards} informs the baseline model documentation.

\section{Datasets}
\label{sec:datasets}

\subsection*{The Common Longitudinal ICU Format}

The Common Longitudinal ICU Format is a critical-care data format that harmonizes ICU electronic health record content into a limited set of relational tables with mCIDE category definitions \citep{rojas2025clif}. FLAIR uses CLIF tables for patients, hospitalizations, admission-discharge-transfer events, vitals, labs, medications, respiratory support, patient assessments, microbiology, diagnoses, and other domains where needed. The current code loads CLIF through \texttt{clifpy} and converts data to local wall-clock timestamps before cohort construction.

CLIF is useful for benchmarking because the task code can refer to common table names and mCIDE category values. This does not remove all site differences, but it reduces the site-specific feature engineering needed before a model can be evaluated. In spirit, CLIF is to critical care what mCODE is to oncology: a clinically scoped common-data-element layer that makes downstream analytic code more portable \citep{mcode2024hl7}. CLIF is complementary to broader EHR machine-learning standards such as the Medical Event Data Standard \citep{arnrich2025meds}. FLAIR can consume CLIF relational tables directly, and future bridges can express CLIF data as event streams for compatible model pipelines.

\subsection*{MIMIC-CLIF}

MIMIC-CLIF is the public development dataset. It expresses MIMIC-IV critical care data in the CLIF v2.1 schema and contains approximately 70,000 ICU stays \citep{johnson2023mimiciv,johnson2016mimiciii}. Developers can use MIMIC-CLIF to debug task definitions, train baselines, and test whether their code follows the cohort and prediction-file contracts before federated execution. This creates a develop-on-public, validate-on-private workflow without requiring private patient-level data to leave consortium sites.

\subsection*{Federated Site Data}

Consortium data are not redistributed. Each site maps its own ICU data to CLIF, runs approved FLAIR code locally, and returns aggregate JSON reports. Across CLIF sites, FLAIR is intended to cover heterogeneous academic medical centers and health systems. \subsection*{Privacy-Preserving Access}

Three properties define the FLAIR access model. First, no patient-level data leave any site; outputs are aggregate JSON reports produced by the FLAIR library inside local execution. Second, the library enforces suppression rules: counts below 10 in cohort tables are suppressed; demographic subgroups with fewer than 10 observations are omitted from subgroup reports; and calibration bins with fewer than 10 observations do not report observed event rates. Third, governance review occurs before execution. The Benchmark Committee reviews submitted code and models for compatibility, clinical face validity, and security concerns before any artifact is distributed to sites. Sites retain final approval over which reviewed submissions run locally.

\section{Benchmarks}
\label{sec:benchmarks}

\subsection*{Task Taxonomy}

Every FLAIR task is described by metadata and implemented as code. The \texttt{META} dictionary records the task class, temporal pattern, prediction unit, label column, clinical threshold, threshold direction, and recommended report mode. The \texttt{build()} function returns a cohort parquet with one row per prediction opportunity. Every row includes a stable \texttt{prediction\_id}, a stitched encounter key, a prediction timestamp, the task label, train/test split, and demographic variables used for reporting. The design keeps the boundary between a new task and an existing task explicit. Reviewers can inspect the metadata before reading the implementation.

\subsection*{Initial Five-Task Suite}

The v1 release covers five binary ICU tasks spanning mortality, disposition, respiratory support, infectious deterioration, and ICU utilization.

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{T1. Daily in-hospital mortality.} At local 07:00 during the first ICU stay, predict whether the hospitalization will end in death or hospice discharge. The current implementation uses an unconditional adult ICU cohort; there is no discharge-disposition filter at cohort entry. The recommended report mode is landmark.
  \item \textbf{T2. Daily LTACH discharge.} At the same daily 07:00 anchors as T1, predict eventual discharge to a long-term acute care hospital. T1 and T2 share the same cohort and grid, but they are not complementary labels. A home discharge is negative for both. The recommended report mode is landmark.
  \item \textbf{T3. Extubation failure within 24 hours.} At the first confirmed extubation after invasive mechanical ventilation, predict death or reintubation within 24 hours. The implementation uses a consensus-window ventilation episode detector to avoid treating short device-status artifacts as true intubation or extubation events. The task targets the respiratory liberation question \citep{thille2011extubation}. The recommended report mode is episodic.
  \item \textbf{T4. Sepsis within 6 hours.} On an hourly hospital-wide grid, predict CDC Adult Sepsis Event onset within the next 6 hours. The current implementation uses the CLIF Adult Sepsis Event utility, includes lactate, requires the CLIF \texttt{microbiology\_culture} table, and stops predictions strictly before the sepsis onset timestamp. This replaces older draft wording that no longer matches the current task code. The recommended report mode is peak. \todo{Confirm all baseline results and captions after this T4 definition is frozen.}
  \item \textbf{T5. Unplanned ICU readmission.} At first ICU discharge, predict return to the ICU later in the same hospitalization through an unplanned path. The label is derived from the ADT location stream. Planned ICU-to-procedure-to-ICU movements are merged and not counted as readmissions. This framing follows structured-EHR ICU-readmission prediction \citep{rojas2018readmission}. The recommended report mode is episodic.
\end{itemize}

\subsection*{Count-Based Reference Baseline}

The reference baseline is an XGBoost model over count features. CLIF events are converted to deterministic tokens in the EHRSHOT/FEMR tradition \citep{wornow2023ehrshot,steinberg2021femr}. Events include vitals, labs, medications, respiratory support, patient assessments, and other configured domains. Each prediction row is represented by counts of events observed before \texttt{prediction\_dttm}. Missing tokens are zero. Tokens not seen during training are ignored at inference. No task-specific feature curation is used in the reference baseline.

The model is trained on MIMIC-CLIF and then frozen for external evaluation. The same trained model and token dictionary are shipped to sites. Per-task clinical thresholds, alarm directions, and report modes are single-sourced in the package policy registry and folded into task audit metadata, so a policy change is visible at every site.

\subsection*{Evaluation Modes}
\label{sec:eval-modes}

FLAIR separates task construction from scoring mode because continuous ICU prediction tasks can be evaluated in more than one way. Episodic scoring is used when there is one prediction per stay, as in extubation failure and ICU readmission. Landmark scoring is used for daily trajectories, as in T1 and T2; it reports performance at lead-time slices before the stay endpoint. Peak scoring is used for continuous screening tasks, as in T4; it collapses each stay to its highest predicted risk before computing discrimination and subgroup metrics. Calibration and decision-curve analysis are omitted for peak mode because taking the maximum of many probabilities distorts probability calibration. This distinction is load-bearing: a row-level metric can overstate the performance a unit would experience when acting on one alarm per stay.

\subsection*{Leaderboard Mechanics}

For each task and site, FLAIR reports AUROC, AUPRC, and threshold-dependent metrics with bootstrap confidence intervals in \texttt{discrimination.json}. Calibration is summarized by slope, intercept, Brier score, and reliability points in \texttt{calibration.json} when the report mode supports calibration. Decision-curve analysis is written to \texttt{dca.json}. Subgroup performance is written to \texttt{fairness.json} across available sex, race, ethnicity, and age strata after suppression. Landmark tasks also write lead-time summaries. The leaderboard ranks submissions on the primary mode-matched metric for each task and displays per-site variation prominently. A single pooled AUROC can hide the failure mode FLAIR exists to surface.

\subsection*{An Open, Extensible Task Catalog}

The five current tasks are the seed of a growing catalog, not a permanent ceiling. Any researcher or clinician can propose a new task as a single Python module in the FLAIR tasks directory containing a \texttt{META} dictionary and a \texttt{build()} function returning the canonical cohort frame. Acceptance review verifies reproducibility against MIMIC-CLIF, clinical face validity through clinician-led review, and site-governance acceptance at a minimum of two consortium sites before the task enters the federated suite. This is the structural counter to benchmark saturation: the catalog can grow with clinical need and community contribution rather than ossifying around one author group's choices \citep{recht2019imagenet,chekroud2024illusory}. \todo{Confirm final task-review committee membership and voting process.}

The federated protocol is what makes FLAIR's privacy properties operational. The actors are explicit. A \textbf{Model Owner} submits a frozen model, code folder, or container. The \textbf{Benchmark Committee}, composed of clinicians, methodologists, and other governance participants, reviews task definitions and submissions for reproducibility, clinical face validity, and security concerns. \todo{Confirm whether regulators and patient representatives should be listed as standing committee roles.} The \textbf{FLAIR Portal} registers tasks, models, sites, and versions; distributes approved artifacts; collects aggregate JSON reports; and renders the leaderboard. At each institution, a \textbf{Site Lead or Data Steward} runs the approved artifact against local CLIF tables and returns only the standardized non-PHI report bundle.

\subsection*{Submission}

A model owner develops against MIMIC-CLIF. The library exposes CLIF tables through \texttt{clifpy}. The benchmark CLI exposes \texttt{flair load-task} to build task-specific cohorts and \texttt{flair build-report} to score predictions into report bundles. A submission may be raw code, a frozen model folder, or a container image that wraps both. Before any model is dispatched to a site, the Portal or review workflow checks that the submission runs against MIMIC-CLIF and follows the prediction-file contract. This model-to-data pattern is not new; it follows the lineage of DREAM Challenges and EHR DREAM \citep{guinney2018dream,bergquist2024ehrdream}. FLAIR's contribution is to turn that competition-style pattern into a standing ICU benchmark and submission service.

\subsection*{Execution}

Each site runs the committee-reviewed, security-approved artifact inside the local CLIF-WorkBench environment or equivalent site-controlled environment. The submitted code may read local CLIF tables, write local cohorts, features, and prediction files, and invoke the FLAIR report builder. Local PHI artifacts remain in site-controlled storage. The intended upload is the aggregate report bundle: cohort summaries, discrimination, calibration where applicable, decision curves where applicable, subgroup summaries, lead-time summaries for landmark tasks, a suppressed code registry, and audit metadata. Every JSON carries the task name, task script hash, FLAIR package version, generation time, report mode, split, number of stays, prevalence, and the operating threshold used for threshold-dependent metrics.

\subsection*{Aggregation, Leaderboard, and Lifecycle}

The central aggregator combines site-level JSON reports for a specific task, model, and version. The leaderboard should show per-site results and per-site variance prominently, because cross-site variation is the evidence FLAIR is designed to expose. Pooled metrics can be shown, but they should not be the only headline. For tasks where sites opt in, the same protocol can support prospective silent-trial evaluation and longitudinal monitoring, consistent with emerging guidance on preregistration and monitoring of clinical AI \citep{goodman2025preregistration,joshi2025silenttrials,pragmaticplaybook2024}. Prospective evaluation is a future protocol extension, not a claim made by the current baseline results.

\subsection*{Comparison With Adjacent Federated Infrastructures}

The closest precedents for federated evaluation are complementary rather than redundant. OHDSI/LEGEND standardizes network studies on OMOP and often shares queries or coefficients \citep{reps2020ohdsistroke}. MedPerf provides hosted-model benchmarking for medical imaging \citep{karargyris2023medperf}. FeTS established federated training for brain MRI segmentation \citep{pati2022fets}. OpenSAFELY moves analytic code to national primary-care data \citep{opensafely2021naturemedicine}. FLAIR contributes the combination needed for ICU EHR-based clinical decision support: CLIF as a critical-care schema, model/code execution at sites, a hosted submission workflow, aggregate-only reporting, and a PR-extensible task catalog.

\section{Toward the Evidence Expected for EHR-Based CDS}
\label{sec:fda}

United States Food and Drug Administration guidance on clinical decision support software and the International Medical Device Regulators Forum framework for software as a medical device ask developers to make the basis of recommendations transparent and to demonstrate validation in the populations of intended use \citep{fda2022cds,imdrf2017samd}. Historically, that posture has been bottlenecked by the same access constraints described above: evidence is generated one bilateral data agreement at a time \citep{finlayson2021clinicianshift,koch2024distributionshift,soin2025shiftremediation}.

FLAIR's contribution to that posture is structural rather than declarative. Byte-identical task code and audit hashes make the cohort definition, exclusions, and outcome label re-inspectable across sites. Per-site discrimination, calibration, subgroup, and cohort JSONs create a mechanically auditable evidence package. Running across heterogeneous CLIF sites without patient-data movement provides a way to observe behavior under realistic distribution shift. FLAIR is not a regulatory submission, not a substitute for prospective clinical trials, and not a guarantee of clinical utility. It is an evidence layer between local model development and the regulator- or clinician-facing claims a developer may eventually want to make.

\section{Discussion}

FLAIR combines three properties that have appeared separately but not together at the scale ICU clinical AI requires: evaluation across heterogeneous sites without patient-data movement, a clinically scoped ICU data format that makes code portable, and a governance protocol that lets the task catalog grow through community contribution.

\paragraph{Saturation resistance through siloed data.} Because FLAIR's private test data remain at participating sites, the data underlying the leaderboard do not enter public hands. This limits the risk that future models are pretrained directly on the evaluation set and reduces the incentive for developers to tune to patient-level private test data they cannot see. FLAIR does not eliminate benchmark gaming or distribution shift, but it makes overfitting to a single public test set less central to the evaluation process.

\paragraph{Why evaluation, not training, federates first.} FLAIR federates evaluation rather than training. That distinction matters. Aggregate metrics leak less patient information than model updates exchanged in federated learning, and the reciprocal risk of exposing a model to sites is bounded by committee review, compatibility checks, and local site approval. Only aggregate, cell-suppressed metrics leave a site. There is no per-site trained model object to share centrally. Evaluation-only federation is also a practical stepping stone toward future federated learning: it establishes a shared schema, code-to-data operations, templated governance, and site trust before any heavier training protocol is attempted.

\paragraph{Limitations.} FLAIR depends on CLIF adoption. Sites that have not mapped their data to CLIF need an extract-transform-load step before they can participate. The current benchmark suite is limited to structured EHR data and binary classification. It does not include notes, waveforms, images, treatment-effect estimation, or prospective bedside impact. Aggregate-only reporting protects privacy but limits fine-grained error analysis. Suppressed small subgroups are not visible in central reports. The current protocol evaluates frozen models; it does not perform federated training. The v2 baseline numbers are useful for manuscript development but should be refreshed after task definitions are frozen, particularly for T4.

\paragraph{Roadmap.} Near-term work should expand site participation, regenerate baselines after final task-code freeze, add site-level columns beyond Rush, and support opt-in prospective silent-trial evaluation. Additional CLIF tables, including diagnoses and procedures, can strengthen future tasks as the schema matures. The same model-to-data contract could later extend to notes, waveforms, and multimodal ICU data if those modalities are standardized within or alongside CLIF. Federated learning is a feasible longer-term extension, but it would require stronger security guarantees, live site-to-server coordination, and separate institutional review.

\paragraph{Conclusion.} FLAIR is a federated benchmark protocol for ICU prediction research. It combines a shared critical-care data format, public development on MIMIC-CLIF, five initial benchmark tasks, committee-reviewed model-to-data execution, and aggregate-only site reporting. Its main contribution is not a new model, but a reproducible way to ask whether ICU prediction models behave similarly across institutions.
