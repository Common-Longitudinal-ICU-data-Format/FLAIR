FLAIR evaluation

Why Daily and Hourly Continuous Tasks Need Different Evaluation

The daily ICU tasks have many rows per stay, but every row shares one final outcome label. An hourly onset task is different: every row asks its own next-hours question. This is why FLAIR needs peak and landmark, and why an hourly onset task needs a special landmark setup. The report unit is always hospitalization_join_id, the full stitched encounter.

1. The Label Shape Is Different

Daily tasks

One final stay label copied across rows

A stay has several daily rows. If the final outcome happened, every daily row gets the same label, such as 1 for death or LTACH.

Question: did this stay eventually have the outcome?

Hourly task

Each row has its own horizon label

Each hourly row asks a new question: will the event happen in the next 6 hours? A patient can have many 0 rows, then some 1 rows near onset.

Question: from this exact hour, is the event coming soon?

Task Rows per stay Label meaning Simple example
Daily tasks many daily rows same final outcome copied to each row death by discharge: 1, 1, 1
Hourly task many hourly rows new next-6-hours label at each hour far from onset then close: 0, 0, 1

2. Daily-Task Calculation: Why Row-Pooling Is Wrong

Setup: three ICU stays. Patient A dies. Patients B and C survive. The model predicts once per day.

Patient Day Predicted risk Label Label meaning
A10.101A eventually died
A20.301same final label copied
A30.601same final label copied
B10.200B survived
C10.050C survived
C20.100same final label copied
  1. True patient-level prevalence: 1 of 3 patients died.
    patient prevalence = 1 / 3 = 33%
  2. Naive row-pooled prevalence: the dying patient has 3 rows, so there are 3 positive rows out of 6 rows.
    row prevalence = 3 / 6 = 50%
  3. Why this is wrong: patient A counts 3 times because A stayed 3 days. Patient B counts once. The report is now partly measuring length of stay, not just model quality.
Takeaway: for the daily tasks, every row has the same final stay label. If we score every row, long stays dominate the result. We need a stay-level reduction.

3. Peak Mode Calculation: The Alarm View

Peak mode keeps one number per stay: the highest risk during the stay. This answers the alert question: did the patient ever cross the threshold?

Patient All risks Peak risk Stay label
A0.10, 0.30, 0.600.601
B0.200.200
C0.05, 0.100.100
  1. One row per stay: now the table has 3 rows, not 6. Each patient counts once.
  2. AUROC by pairs: compare the positive stay A to negative stays B and C.
    A vs B: 0.60 > 0.20 = correct
    A vs C: 0.60 > 0.10 = correct
    AUROC = 2 correct pairs / 2 pairs = 1.00
  3. Alert threshold example: if the threshold is 0.25, A alerts and B/C do not.
    TP = 1, FP = 0, FN = 0, TN = 2
    sensitivity = TP / (TP + FN) = 1 / 1 = 100%
    PPV = TP / (TP + FP) = 1 / 1 = 100%

But peak is not a probability

The peak was selected because it was the biggest number. That makes it useful for ranking and alerts, but bad for calibration. A peak score of 0.60 does not mean "this patient's true risk is exactly 60 percent."

This is why peak mode should not be used for calibration or DCA. Calibration and DCA need honest probabilities.

4. Daily-Task Landmark Calculation: The Probability View

Landmark mode freezes time relative to the stay endpoint. At each landmark, each stay contributes at most one row. That lets the report ask: at this lead time, is the risk number honest?

  2. Run normal report metrics at each landmark. AUROC, calibration, DCA, and fairness now use a clean table.
  3. Repeat over landmarks. The output is a curve: performance at the endpoint, one window earlier, two windows earlier, and so on.

5. Hourly-Task Calculation: Each Row Has Its Own Label

Setup: event onset is at 14:00. The prediction horizon is 6 hours. A row is labeled 1 if onset happens within the next 6 hours from that row.

  1. At 06:00: onset is not within the next 6 hours, so the label is 0.
  2. At 08:00: onset occurs exactly by the end of the 6-hour window, so the label is 1.
  3. At 10:00: onset is inside the next 6 hours, so the label is 1.
  4. At or after onset/treatment: do not keep scoring as if the patient is still at risk. Otherwise the model may look good by reading treatment orders or clinician actions.
Takeaway: an hourly onset task is not "one final label copied across all rows." It is a moving next-hours label. That is why daily-task endpoint landmarking cannot be copied directly onto an hourly onset task.

6. Can We Use Landmarking on an Hourly Task?

Yes, but not the same endpoint landmark used for the daily tasks. An hourly onset task needs a dynamic risk-set landmark.

Landmark type Use for How it works Can use for an hourly onset task?
Endpoint landmark Daily tasks line up rows by windows before the stay endpoint No, not directly
Dynamic risk-set landmark Hourly onset tasks at each hour, include only patients still admitted and event-free Yes

Step-by-step hourly dynamic landmark

  1. Pick a landmark time, such as 08:00.
  2. Keep only patients who are still admitted.
  3. Remove patients who already had the event or already started treatment.
  4. For each remaining patient, take one risk score at 08:00.
  5. Label each patient 1 if the event starts in the next 6 hours, else 0.
  6. Compute AUROC, calibration, DCA, and fairness on that one-row-per-patient table.
  7. Repeat at 09:00, 10:00, and so on to get a curve.

Why peak is still needed for an hourly task

A real deterioration alert often asks: did the model ever cross the alert threshold before treatment? That is a peak question. Dynamic landmark tells us whether risks are honest at specific hours. Peak tells us what the alert system would actually do over the whole encounter.

Bottom Line

Task Label shape Use peak? Use landmark?
Daily tasks one final outcome copied across rows optional alarm view yes, endpoint landmark
Hourly task each row has its own next-hours binary label yes, for alert evaluation before treatment yes, but only dynamic risk-set landmark
One sentence: daily-task landmarking lines patients up before the stay endpoint; hourly-task landmarking lines patients up at a clock time while they are still at risk.
